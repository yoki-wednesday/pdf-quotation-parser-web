# pdf-quotation-parser-web 詳細要件定義書 (Phase 1)

## 1. 背景・課題

### 1.1 背景
* **業務・運用状況**:
  * 岩瀬産業から送られてくる見積回答（PDF）をGmailで受領し、Google Drive for Desktop経由で `Z:\マイドライブ\DATA\ReferenceBook\岩瀬産業\見積回答` フォルダへ保存・蓄積している。
  * 対象のPDFはExcelから出力された**テキストデータ保持PDF（文字選択可能）**であり、OCR処理を介さずにブラウザ内（`pdfjs-dist`）で高精度かつ高速にデータ抽出が可能な条件が整っている。
* **開発の目的**:
  * 受領した見積書PDFをブラウザ上で直接自動解析（クライアントサイド完全パース）し、クラウドデータベース（Supabase / PostgreSQL）へ一元管理する**Web SPA（React + Vite）**を開発する。
  * 過去の見積金額や品名・単価推移を即座に横断検索・比較できるようにし、業務効率化と価格検証の精度向上を図る。
  * まずは岩瀬産業向けとしてシンプルに構築しつつ、**将来的には他商社の見積書PDFも追加・拡張できる構造**を目指す。

### 1.2 課題・検討要素
1. **データ構造化・パース処理の課題**:
   * **ヘッダーと明細の分離**: 見積全体情報（見積番号・日付・合計金額・担当者など）と、複数行に及ぶ明細情報（品名・数量・単価等）をブラウザ内メモリ上で正確に分けて正規化・抽出する必要がある。
   * **文字列のクレンジング**: カンマや円記号（`￥120,420` → `120420`）の数値変換や、品名冒頭のメーカー識別子（例: `<マキタ>`、`<CKD>`）の切り出し処理が必要。
2. **自動化と二重取り込み防止**:
   * クライアントサイドでのハッシュ計算（SubtleCrypto SHA-256）と `import_logs` テーブルによる重複チェックを行い、登録済みファイルを即座に警告・スキップする。
3. **データ精度の担保（確認GUI）**:
   * 自動読み取りだけに頼らず、人間が「原本PDFプレビュー」と「抽出結果グリッド」を見比べながら確認・微修正できる画面（GUI）を挟むことで、DB登録データの正確性を保証する。
4. **将来的な拡張性（マルチ商社対応）**:
   * 初期実装は岩瀬産業に特化させつつも、将来的に他商社のレイアウトが追加された際に、DB構成や全体システムを壊さずに**商社別パーサー（解析ロジック）を後から追加・差し替えできる設計（パーサーの分離）**にしておく。

## 2. 生データ分析・ニーズ構造化 (MUST / SHOULD / COULD)

### MUST (必須機能：第一フェーズ / MVP)
* **仕入見積回答PDFの重複登録防止と保存先案内**
  * 自動監視・自動検出は廃止し、画面上にPDF保存先（`Z:\マイドライブ\DATA\ReferenceBook\岩瀬産業\見積回答` 等）のテキスト案内を表示する。
  * 保存先パスは環境設定（config.json や、GAS環境の場合はスクリプトプロパティ等）で動的に設定可能とする。
  * 手動取り込み時等における、ファイルハッシュ・ログ管理による二重登録防止機能は維持する。
* **PDF自動解析 (パース)**
  * テキストPDFからのヘッダー（見積番号・日付・合計金額等）および明細行（品名・数量・単価等）の自動抽出。
  * データ整形（数値化、品名冒頭からのメーカー名抽出・分割）。
* **確認・修正GUI画面**
  * **2画面プレビュー**: 原本PDF表示 ＋ 抽出データ修正グリッド。
  * 金額不整合（明細合計 ≠ 見積合計）などのバリデーション警告表示。
* **仕入データベース保存 & 過去単価検索**
  * 見積ヘッダー・明細のトランザクション保存と完了ファイルの自動移動。
  * メーカー名・型番・品名ごとの過去の仕入単価推移・履歴比較表示。

### SHOULD (推奨機能：仕入先向け調達ワークフローの完成)
* **新規見積依頼書の生成（対仕入先向け）**
  * 必要な型番・品名・数量を指定し、仕入先へ送付する「見積依頼書（PDF）」を自動生成。
* **新規発注書の生成（対仕入先向け）**
  * DB内の仕入見積回答データを引き継ぎ、仕入先への「正式発注書（PDF）」を1クリックで自動生成。
* **Gmail下書き自動作成（Gmail API連携）**
  * 見積依頼書や発注書PDFの生成時、Gmail APIを介して宛先・件名・本文・PDF添付が完了した「下書き」を自動生成。
* **調達ステータス管理**
  * 案件ごとに仕入先との進捗状態（`見積依頼中` ➔ `見積回答済` ➔ `発注済` ➔ `入荷待ち` ➔ `完了`）を可視化・管理。
* **マルチ商社対応（パーサー拡張基盤）**
  * 岩瀬産業以外の仕入先PDFも後から追加できる共通設計（パーサー分離構造）。

## 4. ユースケース

1. **見積データ取り込み**
   * ユーザーがアプリを起動する。
   * アプリが `Z:\マイドライブ\DATA\ReferenceBook\岩瀬産業\見積回答` フォルダを走査し、未処理のPDF一覧を取得する。
   * ユーザーが処理対象のPDFを選択（または一括処理）する。
   * アプリがPDFからテキストを抽出し、ヘッダー情報と明細情報にパースする。
   * ユーザーが「2画面プレビュー（PDF原本と抽出結果グリッド）」で内容を確認し、必要に応じて金額の不整合や文字化けを微修正する。
   * ユーザーが「保存」を実行し、アプリがDBにデータを記録。ファイルは処理済みとしてマーク（または移動）される。
2. **過去単価検索**
   * ユーザーが検索画面から、メーカー名、型番、品名などのキーワードを入力する。
   * アプリが該当する過去の仕入明細履歴を一覧表示し、単価推移や最安値を比較できるようにする。
3. **（SHOULD）見積依頼・発注書生成・Gmail連携**
   * ユーザーが必要な部材を指定し、「見積依頼書生成」または「発注書生成」を実行する。
   * アプリがPDFを自動生成し、Gmail API経由で下書きを作成する。
   * ユーザーがブラウザ等でGmailの下書きを目視確認し、送信する。

1. **ファイル監視・取り込み機能**
   * 指定ディレクトリの読み込み機能。
   * 処理済みファイル管理機能（ファイルハッシュ生成、`import_logs` テーブルによる重複チェック）。

4. **データベースアクセス機能 (Supabase BaaS / PostgreSQL)**
   * クラウドデータベース（Supabase PostgreSQL + RLS）へのCRUD操作。

5. **(SHOULD) 帳票生成・外部連携機能**
   * 見積依頼書、発注書のPDF出力機能。

## Loop 3 差分セクション (帳票テンプレート仕様改定)

### 1. 背景・課題
* **背景・目的**:
  欧米式レイアウト（Helvetica/英語表記/WinAnsi制限）から、日本の商習慣に準拠した実用的かつシンプルな「日本企業向け帳票仕様」へ改定する。不要な検印欄や社印枠、不要な税サマリー・条件欄を排除し、業務実態に即した帳票レイアウトを確定する。

### 2. 生データ分析・ニーズ構造化 (MUST / SHOULD / COULD)

#### MUST (必須機能)
* **フォント・日本語エンコーディング基盤**:
  * `@pdf-lib/fontkit` を導入し、オープンソースおよびシステム日本語フォント（`Noto Sans JP` / `YuMincho` 等）をバイナリ埋め込み。
  * `sanitizeText` による非ASCII文字置換（`?` 化）を廃止し、漢字・ひらがな・カタカナ・全角記号を完全描画。
* **表題および取引先・発行元レイアウトの日本語化**:
  * 帳票表題（見積依頼書: `「御 見 積 依 頼 書」`、発注書: `「御 発 注 書」`）。
  * 宛名表記: 商社・仕入先名 + `「御中」`、担当者名 + `「様」`。
  * 自社情報: 自社名、郵便番号・住所、TEL/FAX、担当者名（※ 社印枠・インボイス登録番号は不要・非表示）。
* **帳票種別ごとの金額・明細レイアウト制御**:
  1. **御見積依頼書 (`ESTIMATE_REQUEST`)**:
     * **挨拶文**: `「下記の通りお見積りをご依頼申し上げます。」`
     * **金額表記**: **非表示**（仕入先に価格提示を求めるため、合計金額欄は出力しない）。
     * **明細テーブル (5カラム)**: `項番`、`メーカー名`、`品名・型番 / 仕様`、`数量/単位`、`備考 / 希望納期`（※ `単価`・`金額` は非表示とし、品名・備考幅を拡張）。
  2. **御発注書 (`PURCHASE_ORDER`)**:
     * **挨拶文**: `「下記の通りご発注申し上げます。」`
     * **金額表記**: `ご発注金額: 〇〇〇,〇〇〇 円`（税抜合計額を下線強調表示。※ 消費税額・税込合計の内訳サマリーは不要・非表示）。

     * **明細テーブル (7カラム)**: `項番`、`メーカー名`、`品名・型番 / 仕様`、`数量/単位`、`単価 (税抜)`、`金額 (税抜)`、`備考 / 納期`。
* **取引条件枠の簡素化**:
  * 取引条件枠は `「【希望納期】」` および `「【受渡場所】」` の2項目のみを表示（※ `お支払条件`、`見積有効期限` は不要・非表示）。
* **不要要素の完全排除**:
  * **社印（角印枠）**: 不要・非表示。
  * **承認印欄（承認・審査・担当の3連検印枠）**: 不要・非表示。

## Loop 6 差分セクション (PDF ファイル選択・ドロップ → テキスト自動抽出連携)

### 1. 背景・課題
* **背景・目的**:
  * 現状、GUIの「原本テキスト & PDF入力」ペイン（`#raw-text-viewer`）には岩瀬産業サンプルのハードコードされたテキストが初期表示されている。ユーザーが実際のPDFを取り込むには手動でテキストを貼り付けるしかなく、実運用上の操作負荷が高い。
  * 画面上でPDFファイルをドロップ、またはファイル選択ダイアログから選択することで、サーバー側がPDF→テキスト抽出を行い、その結果をテキストエリアに自動反映する連携処理を実装する。
* **影響範囲**:
  * フロントエンド: `src/gui/public/index.html`（ドロップゾーンUI・ファイル選択ボタン・アップロードリクエスト送信）
  * バックエンド: `src/server.ts`（`/api/upload-pdf` エンドポイント新設）
  * PDF抽出処理: `src/importer/` 配下の既存ロジック活用、または `pdf-parse` / `pdfjs-dist` 等既導入ライブラリを経由

### 2. 生データ分析・ニーズ構造化 (MUST / SHOULD / COULD)

#### MUST (必須機能)
* **ドロップゾーン UI の実装**:
  * 「原本テキスト & PDF入力」ペインにファイルドロップ対応エリアを設置する。
  * ドラッグオーバー時に視覚的ハイライト（枠色変化）を表示する。
  * `.pdf` 以外のファイルをドロップした場合はエラーメッセージを表示し処理しない。
* **ファイル選択ダイアログからの選択**:
  * `<input type="file" accept=".pdf">` による明示的ファイル選択をサポートする。
* **クライアント → サーバー PDF アップロード**:
  * `multipart/form-data` で PDF バイナリを `POST /api/upload-pdf` へ送信する。
  * アップロード中はローディング状態を表示し、完了後にテキストエリアへ抽出テキストを反映する。
* **サーバー側 PDF テキスト抽出**:
  * `/api/upload-pdf` エンドポイントを新設し、受信した PDF バイナリから既存パース基盤（`pdf-parse` 等）を用いてテキストを抽出してレスポンスする。
* **抽出テキストのテキストエリア自動反映**:
  * 抽出完了後、`#raw-text-viewer` の内容を抽出テキストで置換し、即座に再パース（`/api/parse`）を実行してパース結果グリッドへ反映する。

#### SHOULD (推奨機能)

* **背景・目的**:

#### MUST (必須機能)
* **主キーのUUIDv7化**:
  * `estimates`, `estimate_items`, `import_logs`, `procurement_projects`, `product_master` の全テーブル主キーを `TEXT` 型の UUIDv7 に移行する。

* **状態（Status）管理カラムの導入**:
  * `estimates` テーブルに `status` カラムを追加し、初期値 `'draft'` およびワークフロー遷移（`draft`, `pending`, `approved`, `ordered`, `rejected`）を制御する。
* **論理削除（deleted_at）のサポート**:
  * 全主要テーブルに `deleted_at DATETIME` カラムを追加し、データ参照（`SELECT`）時は `WHERE deleted_at IS NULL` を適用して物理削除による監査証跡喪失を防止する。
* **非定型JSONメタデータカラムの導入**:
  * `metadata TEXT`（JSON文字列）カラムを追加し、OCR抽出の生情報や将来の拡張属性を柔軟に格納可能にする。

### 3. ゴール(KPI)
* **ゴール**:
  * 既存機能・全自動テストの互換性を100%維持しながら、将来の分散スケールアウトおよび財務データの完全性を担保する。
