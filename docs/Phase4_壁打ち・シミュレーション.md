# Phase 4 壁打ち・シミュレーション (Simulation & Triage)

本ドキュメントは、Phase 1〜3で定義された仕様（要件、データ設計、アーキテクチャ）に対し、技術エッジケース、セキュリティ脅威、UX誤操作の3視点から最悪の障害シナリオを想定し、客観的なリスク評価と優先対処策のトリアージを行った結果です。

## 1. 視点1：技術・エッジケース検証

| リスクシナリオ | 影響度 | 詳細・最悪の結末 |
| :--- | :--- | :--- |
| **1-1. PDF解析によるメインスレッド枯渇（ブラウザフリーズ・OOM）** | Critical | `pdf.js`によるパース処理はCPUバウンドです。数十〜数百ページに及ぶ巨大な見積書や、高解像度画像が埋め込まれた非標準的PDFがD&Dされた場合、ブラウザのメインスレッドをブロックし、タブのクラッシュやOSレベルのフリーズを引き起こす可能性があります。 |
| **1-2. 非テキスト化PDF・暗号化PDFの処理破綻** | High | スキャンされた画像ベースのPDFや、パスワード保護（DRM）されたPDFが投げ込まれた場合、`pdf.js`のテキスト抽出が空（またはエラー）を返し、後続の正規化ロジックが未定義動作（`undefined`参照によるJS例外）を引き起こしアプリが操作不能に陥ります。 |
| **1-3. 同一内容・メタデータ差異による重複突破** | High | SHA-256で重複排除（`document_hash`）を行っていますが、PDFツールで「保存し直しただけ」の同一見積書でもメタデータやタイムスタンプが変わるためハッシュ値が変化し、重複取り込みブロックをすり抜けて二重発注を誘発するリスクがあります。 |

## 2. 視点2：セキュリティ・堅牢性検証

| 攻撃ベクトル・リスク | 影響度 | 詳細・最悪の結末 |
| :--- | :--- | :--- |
| **2-1. RLSバイパス（INSERT時の権限昇格・汚染）** | Critical | RLSは `auth.uid() = user_id` で分離していますが、SupabaseのINSERTポリシーにおいて `WITH CHECK` 句が漏れている場合、悪意のあるユーザーがAPIリクエストのペイロードで他社の `user_id` （UUID）を偽装してデータをINSERTでき、他社テナントのデータを破壊・汚染するリスクがあります。 |
| **2-2. 抽出テキスト経由のXSS（Stored/Reflected XSS）** | Critical | 攻撃者が細工したPDF内に `<script>...</script>` 等のペイロードを仕込み、テキストとして抽出されたものをReactのプレビューグリッドで危険なレンダリング（例: `dangerouslySetInnerHTML`等の不適切な使用）を行った場合、ブラウザ内でスクリプトが発火し、セッショントークンが窃取されます。 |
| **2-3. バッチINSERT時のトランザクション不整合** | High | `estimates`（ヘッダ）と `estimate_items`（明細）をREST APIから保存する際、ネットワーク切断により「明細だけ保存されてヘッダがない（またはその逆）」という孤立データ（Orphan Data）が発生し、システムエラーの温床となります。 |

## 3. 視点3：UX・ユーザーエラー検証

| 誤操作シナリオ | 影響度 | 詳細・最悪の結末 |
| :--- | :--- | :--- |
| **3-1. 大量編集後の意図せぬタブ閉じ・遷移によるデータ消失** | High | 抽出された見積明細（50行など）に対し、手動で単価や商品名を時間をかけて修正している最中に、ユーザーがブラウザの「戻る」ボタンやタブの×ボタンを誤操作した場合、警告なしに全編集データが消失し、強いユーザーストレスと離脱を招きます。 |
| **3-2. 買い物かごの二重決済（二重PDF生成・重複保存）** | High | 「見積依頼書を生成して保存」ボタンの非同期処理中にローディング制御（ボタンのDisable化）が不十分な場合、ユーザーが連打することで同一の履歴データが複数件登録され、取引先に誤って複数回見積依頼を出してしまう致命的なヒューマンエラーを誘発します。 |

## 4. 周回進行推奨判定

**判定: New Loop [次周移行]**

**【判定理由】**
コアとなるアーキテクチャ（BaaS / Serverless SPA）自体を根本から覆すような致命的な設計破綻は検出されませんでした。特定されたCriticalリスクは、Web Workerの導入、RLSポリシーの厳格化、トランザクション処理用RPCの追加実装といった、**実装タスクの追加・詳細設計への反映**によって吸収可能です。そのため、現在の設計を現周回で全て破棄（Rollback）するのではなく、次周の実装計画（Taskify）としてアクションを積み上げることで安全に前進できます。

## 5. 総合改善提案 & トリアージ済み優先対処アクションマトリクス

| 指摘項目 (リスクID) | 影響度 | triageCategory | actionDetails (一時対応策・代替案) |
| :--- | :--- | :--- | :--- |
| 1-1 (PDFパースフリーズ) | Critical | **Taskify** | `pdf.js`の解析処理をメインスレッドから分離し、**Web Worker** 内で実行するタスクを追加（REQ-22-001の拡張）。 |
| 1-2 (非テキスト/暗号化PDF) | High | **Taskify** | 解析前バリデーションを実装。暗号化フラグや抽出テキスト文字数が閾値以下の場合にエラーUIを即時表示し、処理を中断させる。 |
| 1-3 (ハッシュすり抜け) | High | **Defer** | 現状はファイルハッシュのみでブロックし、運用回避（担当者の目視確認）とする。完全な明細ハッシュ化は次期要件（Future）へ退避。 |
| 2-1 (RLS INSERT汚染) | Critical | **Taskify** | DBのRLS定義（マイグレーションSQL）において、INSERT時に `WITH CHECK (user_id = auth.uid())` を強制する設定タスクを確実に追加。 |
| 2-2 (PDF経由のXSS) | Critical | **Taskify** | Reactの標準エスケープ（JSX）を維持し、DOMを直接操作しないことをコーディング規約化。万が一HTMLレンダリングが必要な場合は `DOMPurify` を必須化。 |
| 2-3 (ヘッダ・明細の不整合) | High | **Taskify** | RESTによる複数回リクエストを廃止し、Supabaseの **Postgres RPC (Stored Procedure)** を呼び出して1トランザクションでヘッダと明細を一括コミットするタスクへ変更。 |
| 3-1 (編集データ消失) | High | **Taskify** | `beforeunload` イベントを利用した未保存警告ダイアログの実装、および `localStorage` への編集状態の一時退避（オートセーブ）をタスク化。 |
| 3-2 (ボタン連打二重処理) | High | **Taskify** | 処理開始時にグローバルなUIロック（オーバーレイ表示）と対象ボタンの `disabled={true}` 化を徹底し、ローディングステート管理を追加。 |
